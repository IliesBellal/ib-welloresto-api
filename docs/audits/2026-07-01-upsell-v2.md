# Audit upsell v2 (comparatif /orders/upsell vs /scannorder/upsell + refactor cache Redis)

Audit read-only en deux parties : (1) comparatif entre l'endpoint upsell POS (`/orders/upsell`) et l'endpoint upsell SNO (`/scannorder/{slug}/upsell`), (2) évaluation de la faisabilité d'un refactor du cache Redis en cache par produit et d'une unification de la logique upsell entre POS et SNO.

---

## Partie 1 — Comparatif /orders/upsell (POS) vs /scannorder/upsell (SNO)

### 1. Endpoint /orders/upsell (POS)

**Routing** — [routes.go:916](cmd/api/routes.go#L916), dans le groupe `r.Route("/orders", ...)` qui applique `r.Use(authMiddleware)` ([routes.go:910-911](cmd/api/routes.go#L910-L911)). Auth par **bearer token classique** (même middleware que tout le reste du POS), utilisateur extrait via `middleware.UserFromContext(ctx)`.

**Chaîne** : `OrdersHandler.GetUpsell` ([internal/modules/orders/handler.go:128-173](internal/modules/orders/handler.go#L128-L173)) → `upsell.Service.GenerateUpsell` ([internal/modules/upsell/service.go:90](internal/modules/upsell/service.go#L90)) → `upsell.Repository`.

**Appelant** : confirmé exclusivement le POS Flutter — [upsell_api_service.dart](d:\Desktop\DTL\Project\git-projects\wello_resto_flutter\lib\data\api\upsell_api_service.dart) appelle `POST /orders/upsell` via `ApiRequestMiddleware` (bearer token du POS), en cas d'erreur il retombe silencieusement sur un résultat vide (upsell "non bloquant").

**Paramètres reçus** (`models.PricingRequest`, body JSON) :
- `order.products[]` (panier courant : product_id, name, price, quantity)
- `order.order_type` (IN / TAKE_AWAY / DELIVERY)
- **Pas** de `order_id` ni `merchant_id` explicite — le `merchant_id` vient du token (`user.MerchantID`).

**Logique de sélection** — cascade à 3 niveaux dans `generateUpsellSafe` :
1. **Vérif activation** : `enable_upsell` + `upsell_max_items` dans `merchant_parameters` (repo `GetMerchantUpsellSettings`). Si désactivé → `source: "disabled"`, liste vide.
2. **Cache résultat** : clé Redis `upsell:result:{merchant}:{cartSignature}:{orderType}`, TTL 30 min.
3. **Pattern Apriori** (Redis `upsell:patterns:{merchant}:{productID}`, alimenté par un cron `RecomputePatterns` — actuellement déclenché uniquement à la main via `/admin/upsell/recompute-patterns`, cf. cron désactivé dans `SetupTasks`). Score = somme des lifts agrégés sur tous les produits du panier ; retenu seulement si `bestLift >= 1.5` **et** assez de candidats.
4. **Fallback LLM** (Anthropic/OpenAI via `ai.Registry`, tâche `upsell`, prompt JSON avec panier + produits dispo + paires fréquentes), avec anti-hallucination (rejette tout `product_id` hors du candidate set) et 1 retry.
5. **Fallback final** : `ListFeaturedProducts` (produits "featured" statiques), toujours persisté même si vide.

C'est donc **fondamentalement dynamique et contextuel au panier courant** — rien à voir avec un simple `is_popular` statique.

**Construction produit dans la réponse** (`SuggestedItem`, [types.go:38-45](internal/modules/upsell/types.go#L38-L45)) :
```go
ProductID, Title (phrase générée), Score, Name, Price (int64, prix "de base"), ImageURL *string
```
→ **Champs plats uniquement**. Pas d'attributs, pas d'options, pas de `configuration`. C'est exactement la situation **avant** le fix sur `/scannorder/upsell` : les données viennent de `menu.ListAvailableProductsForUpsell` (jointure légère produit+catégorie), pas de `GetProductFromMerchantId` complet. Si un produit suggéré a des options obligatoires, le POS devra faire un second appel pour charger la fiche complète avant d'ouvrir la modale de configuration (à vérifier côté Flutter, mais rien côté API ne le fournit).

**Tracking** — oui, complet et déjà en place :
- Table de suggestions persistée à chaque appel (`upsell.Repository.CreateSuggestion`) avec `suggestion_id`, `cart_signature`, `suggested_items`, `source`, tokens/latence LLM.
- `suggestion_id` renvoyé au client, réinjecté dans `RequestObject.UpsellSuggestionID` à la création de commande.
- `OrdersLifeCycleService.CreateOrder` ([internal/modules/order_life_cycle/service.go:963-987](internal/modules/order_life_cycle/service.go#L963-L987)) déclenche alors `upsellTracker.TrackAsync` (fire-and-forget, goroutine isolée) qui recoupe `finalProducts` de la commande avec les `suggested_items` et persiste `accepted_items` + `revenue_impact` via `RecordAcceptance`.

### 2. Endpoint /scannorder/{slug}/upsell (SNO) — état actuel

Confirmé sans ambiguïté :
- Auth par QR code uniquement (`GetMerchantIDAndTZFromQR`), aucun `authMiddleware`, route publique.
- Sélection statique : `GetUpsellProducts` = `is_popular = 1 AND status IN ('available','1') AND (is_product_group IS NULL OR != 1)`, triés par nom — pas de lien avec le panier courant.
- Construction produit via `menu.GetProductFromMerchantId` **par produit** (appel complet, comme la fiche produit), suivi de `cleanProductForSNO` → réponse pleinement configurée (attributs, options, prix par canal).
- Cache Redis `scannorder:merchant:upsell:{qr}` avec TTL identique au menu, pas d'invalidation active (TTL seul).

**Tracking** : **aucun**. Ni suggestion persistée, ni `suggestion_id`, ni `UpsellSuggestionID` transmis à `CreateOrderSNO`. Fait notable : `CreateOrderSNO` appelle bien `s.orderLifeCycleSvc.CreateOrder` (même fonction que le POS, donc le hook de tracking existe déjà dans le code partagé), mais le `RequestObject` construit ligne 827 ne renseigne jamais `UpsellSuggestionID` — donc même si on branchait le tracking demain, il faudrait d'abord que le SNO génère un `suggestion_id` à conserver.

| Axe | `/orders/upsell` (POS) | `/scannorder/upsell` (SNO) |
|---|---|---|
| Appelant | POS Flutter uniquement (bearer) | Client SNO (QR, web/app client) |
| Auth | `authMiddleware` (token Redis) | QR code embarqué dans l'URL, pas de middleware |

| Cache Redis | Oui (résultat 30 min + patterns Apriori) | Oui (résultat, TTL menu) |

### 4. Faisabilité de fusion

- **Logiques de sélection incompatibles par nature** : Apriori/LLM contextuel au panier (POS) vs liste statique `is_popular` (SNO). Fusionner les *algorithmes* n'a pas de sens — un client SNO qui n'a encore rien ajouté au panier au moment de charger la page n'a pas de "panier courant" à analyser dans le même esprit (bien qu'on pourrait imaginer réutiliser Apriori une fois le panier non-vide, ce n'est pas la maquette actuelle du SNO).
- **Auth différente n'est pas un obstacle réel** : les deux endpoints résolvent un `merchant_id` en amont (token pour POS, QR pour SNO) avant d'appeler la couche métier — c'est déjà abstrait au niveau service (`merchantID string` en paramètre partout). Un endpoint unique pourrait techniquement accepter les deux mécanismes d'auth sans changer la logique interne.
- **Mise en commun de la couche de construction produit** : oui, c'est le point le plus rentable et le moins risqué. Le POS gagnerait à charger les produits suggérés via `GetProductFromMerchantId` + un `cleanProductForSNO`-like (renommé neutre) plutôt que la jointure légère actuelle, pour éviter l'exact problème déjà corrigé côté SNO (pas de configuration/attributs). C'est un chantier localisé au remplissage de `SuggestedItem`, sans toucher à la logique de sélection ni au tracking.
- **Risque de régression sur le POS** : réel si on touche à `/orders/upsell` sans précaution — le pipeline Apriori/LLM/cache/tracking est bien plus complexe et déjà en prod avec économie de coûts LLM (cache 30 min, seuil de lift). Enrichir `SuggestedItem` avec la config produit implique un appel supplémentaire par suggestion (comme le fait déjà SNO), donc un coût de latence à mesurer, et il faudra adapter `parseLLMResponse`/`persistAndCache` pour ne pas casser le cache existant (le cache stocke actuellement les champs plats).

### Conclusion (partie 1)

**Recommandation : mise en commun partielle — uniquement la couche de construction produit, pas de fusion des endpoints.** Les deux logiques de sélection (contextuelle/IA vs catalogue statique) et les deux modèles d'auth répondent à des besoins produit différents et n'ont pas vocation à converger. En revanche, extraire un helper commun `menu.GetProductFromMerchantId` + nettoyage pour enrichir les `SuggestedItem` du POS avec la configuration complète corrigerait une vraie dette (même bug que le fix SNO) à moindre risque, sans toucher au tracking ni à la logique Apriori/LLM déjà en prod.

**Point bloquant à trancher avant d'implémenter** : le coût de latence d'un appel `GetProductFromMerchantId` par suggestion sur le POS (jusqu'à `upsell_max_items`, potentiellement plusieurs appels séquentiels) dans un flux qui a un budget serré (`llmTimeout = 1500ms`) — à chiffrer avant de généraliser.

## Partie 2 — Refactor cache Redis (produits individuels) + unification logique upsell

### 1. État actuel du cache Redis (module scannorder)

Toutes les clés sont préfixées et définies dans [internal/models/redis_models.go:18-26](internal/models/redis_models.go#L18-L26), utilisées uniquement via le wrapper `internal/infrastructure/redis.Client` (Get/Set bruts, pas de structure avancée) :

| Clé | Valeur stockée | TTL | Invalidation |
|---|---|---|---|
| `scannorder:merchant:{qr}` | `MerchantResponse` JSON complet (infos merchant, currency, couleurs, frais livraison, etc.) | 60 min | Aucune — TTL seul |
| `scannorder:merchant:menu:{qr}:{deliveryType}` | `MenuResponse` JSON complet (catégories + produits déjà flattenés/nettoyés pour ce `deliveryType`) | 10 min | Aucune — TTL seul |
| `scannorder:merchant:upsell:{qr}` | `UpsellResponse` JSON (produits `is_popular`, déjà nettoyés, **sans** distinction de `deliveryType` — prix "défaut" uniquement) | 10 min | Aucune — TTL seul |

**Point critique non demandé mais structurant pour la suite** : les clés sont indexées par **QR code** (`qrcodes.code`), pas par `merchant_id`. Or `qrcodes` a une colonne `location_id` ([repository.go:45](internal/modules/scannorder/repository.go#L45)) — un QR est associé à une table/localisation, pas au merchant globalement. Un restaurant avec 20 tables a donc potentiellement **20 QR codes distincts pointant vers le même merchant**, et le menu (identique) est dupliqué 20× dans Redis, chacun expirant indépendamment et recalculé indépendamment à froid. C'est un axe d'optimisation orthogonal mais très pertinent pour justifier le refactor : clé sur `merchant_id` (+ `deliveryType`) élimine cette duplication d'un coup, indépendamment du passage au cache produit-par-produit.

Une fonction `DeleteAllMerchantKeys` existe déjà ([redis/client.go:88-101](internal/infrastructure/redis/client.go#L88-L101)) mais scanne le pattern `scannorder:merchant:{merchantID}*` — donc ne matchera **jamais** les clés réelles (indexées par QR, pas par merchant_id). Le commentaire dans `service.go:1087-89` confirme que cette fonction n'est appelée nulle part actuellement — c'est un bug latent déjà identifié par l'équipe, pas une découverte nouvelle, mais il faudra le corriger ou le supprimer dans le cadre de tout refactor de clé.

**`MenuRepository.GetMenu`** ([repository.go:616](internal/modules/menu/repository.go#L616)) — la fonction derrière `GetMenuFromMerchantIdWithMarketing` :
- **10 requêtes SQL au total**, toutes batchées par `merchant_id` (pas de N+1 par produit) : `last_menu_update`, `categories`, `products_roots` (avec 3 JOIN tva + LEFT JOIN self), `sub_products`, `components_requires`, `configurable_options` + `configurable_attributes`, `allergens`, `tags`, `delays`, `component_categories` + `all_components`.
- `GetMenuWithMarketingCategories` ajoute 1 requête de plus (`product_marketing_categories`).
- **Total ≈ 11 requêtes SQL pour tout le menu**, indépendamment du nombre de produits. C'est déjà efficace côté volumétrie de requêtes — le vrai point chaud n'est pas là.
- Volume typique : pas de moyen fiable d'estimer le nombre moyen de produits par merchant sans accès aux données de prod (pas de requête `COUNT` exécutable dans cet audit). À titre indicatif d'ordre de grandeur d'un menu de restaurant classique (structure `productcateg` + `products` avec groupes/sous-produits), on est généralement dans une fourchette de quelques dizaines à ~150-200 lignes produit (racine + sous-produits confondus) — à vérifier en DB si un chiffre exact est nécessaire pour trancher.

Le vrai point chaud, documenté dans le commentaire du code lui-même ([service.go:1076](internal/modules/scannorder/service.go#L1076) *"calcul lourd : 1 GetProduct par produit populaire"*), c'est `computeGetUpsell` : **`MenuRepository.GetProduct` exécute 6 requêtes SQL par produit** (produit, components, configurable_options, configurable_attributes, allergens, tags — [repository.go:2175-2433](internal/modules/menu/repository.go#L2175-L2433)), appelée en boucle une fois par produit `is_popular`. Pour un merchant avec 8 produits populaires, ça fait **48 requêtes SQL séquentielles** à chaque cache miss upsell (toutes les 10 min).

### 2. Faisabilité du cache par produit

**Stabilité/sérialisabilité de `ProductEntry`** ([internal/models/menu_models.go:24-83](internal/models/menu_models.go#L24-L83)) : struct plate, uniquement primitives, pointeurs, slices et sous-structs avec tags JSON — aucun `sql.Null*`, channel, ou fonction embarqués. **Parfaitement sérialisable en JSON pour Redis**, sans transformation nécessaire.

**Attention cependant** : `GetProduct` (utilisée pour la fiche produit unitaire et l'upsell SNO) ne remplit **pas** le champ `SubProducts` — ce champ n'est peuplé que par le `GetMenu` batché (via les steps 3+4). Un cache "produit individuel" alimenté par `GetProduct` ne pourra donc pas, à lui seul, reconstruire la hiérarchie parent/groupe nécessaire au menu complet. Il faudrait soit enrichir `GetProduct` pour charger les sous-produits, soit maintenir un index séparé des relations `by_product_of` en parallèle du cache produit.

**Flattening + `cleanProductForSNO`** : la fonction ([service.go:1149-1192](internal/modules/scannorder/service.go#L1149-L1192)) **doit rester une dérivation à la lecture**, pas une transformation à cacher en amont, pour une raison structurelle précise : `cleanProductPricesForSNO` collapse les 4 champs de prix (`Price`, `PriceDelivery`, `PriceTakeAway`, `PriceDeliveroo/UberEats`) en un seul `Price` **selon le `deliveryType` passé en paramètre**, puis met les autres à `nil`. C'est donc une fonction **pure de `(ProductEntry brut, deliveryType) → ProductEntry nettoyé`**, non idempotente et non réutilisable entre canaux : si on la cache déjà appliquée, il faut un cache par `deliveryType` (× 3), ce qui recrée la même duplication qu'aujourd'hui. En cachant le `ProductEntry` **brut** (post-`GetProduct`, pré-nettoyage) et en appliquant `cleanProductForSNO` à la lecture (coût CPU pur, pas de DB), on obtient un seul enregistrement par produit servant tous les `deliveryType` et items de flattening (menu, fiche produit, upsell) — c'est net techniquement supérieur à l'existant.

**Données hors produit à garder dans un cache "menu" séparé** :
- `productcateg` (catégories, ordre d'affichage, couleurs) — table indépendante des produits.
- `product_marketing_categories` (overrides marketing) — relation many-to-one produit→catégorie marketing, recalculée dans `GetMenuWithMarketingCategories`.
- Les relations `by_product_of` (groupe → sous-produits) mentionnées ci-dessus.
- `LoyaltyPrograms` et `Discounts` (déjà hors du cache Redis actuel — calculés à chaque `GetMenu`, pas mis en cache du tout aujourd'hui, à noter au passage).

Donc l'architecture cible logique serait : **cache produit individuel** (`product:{merchant_id}:{product_id}` → `ProductEntry` brut) + **cache structure** (`menu:structure:{merchant_id}` → liste ordonnée de category→product_id[] + display_order + marketing overrides), le menu complet étant reconstruit en joignant les deux à la lecture.

### 3. Coût N appels Redis vs 1 appel monolithique

**Le client actuel ne supporte ni MGET ni pipelining** — [internal/infrastructure/redis/client.go](internal/infrastructure/redis/client.go) n'expose que `Get`/`Set`/`Delete`/`DeleteAllMerchantKeys`/`ScanDeleteByPattern`, un `Get` = une commande réseau. La lib sous-jacente (`github.com/redis/go-redis/v9`) supporte nativement `MGet` et `Pipeline()`, mais **rien n'est exposé par le wrapper** — c'est un ajout de code obligatoire avant toute variante (b) ou (c), pas une réutilisation.

Comparatif qualitatif (pas de bench réel possible dans cet audit read-only) :
- **(a) 1 GET monolithique** : 1 aller-retour réseau Redis. Coût réseau minimal, mais payload JSON plus gros à désérialiser (tout le menu d'un coup) et cache invalidé/regénéré en bloc (moindre granularité — changer un seul produit invalide tout le menu).
- **(b) N GET séquentiels** : N allers-retours réseau **séquentiels** = latence ≈ N × (RTT réseau + temps de traitement Redis). Sur un Redis colocalisé ou proche (< 1ms RTT), N=50 produits ≈ 50ms de latence ajoutée rien qu'en réseau, ce qui casse le budget `llmTimeout=1500ms` du module upsell POS si on veut un jour partager la couche produit. **À proscrire.**
- **(c) 1 MGET (ou pipeline)** : 1 aller-retour réseau pour N clés = latence proche de (a), avec l'avantage de la granularité d'invalidation individuelle. C'est la seule variante acceptable en pratique — mais elle nécessite d'ajouter une méthode `MGet(ctx, keys []string) map[string]string` (ou équivalent pipeline) au wrapper.

**Conclusion de cette section** : le passage à un cache par produit n'a de sens que si on l'accompagne systématiquement de MGET/pipeline — jamais de boucle de GET séquentiels. C'est un prérequis technique de la Phase A, pas un détail d'implémentation.

### 4. Unification logique upsell

**Confirmé** : `upsell.Service.GenerateUpsell(ctx, merchantID string, cartProducts []models.ProductEntry, orderType string) (*UpsellResult, error)` ([internal/modules/upsell/service.go:90](internal/modules/upsell/service.go#L90)) ne prend que des paramètres primitifs/DTO — **aucune dépendance à `middleware.UserFromContext`, aux permissions RBAC, ou à un `staff_member_id`** dans tout `service.go`, `repository.go`, `tracker.go` du module upsell. La résolution de `merchant_id` se fait **avant** l'appel, côté handler (`user.MerchantID` pour le POS). Un handler SNO résolvant `merchantID` via `s.repo.GetMerchantIDAndTZFromQR(ctx, qr)` (déjà fait dans `computeGetUpsell`) peut appeler `GenerateUpsell` directement, sans aucun contournement ni contexte utilisateur factice. **C'est directement appelable depuis SNO tel quel.**

**Table `upsell_suggestions`** : colonnes connues via les requêtes du repository — `id, merchant_id, cart_signature, suggested_items, source, llm_provider, llm_model, tokens_in, tokens_out, latency_ms, order_id, accepted_items, revenue_impact, created_at, staff_member_id`. **Aucune colonne "canal" (POS/SNO)** — `source` désigne déjà l'origine algorithmique (`pattern`/`llm`/`featured_fallback`/`disabled`), pas le canal d'appel. `staff_member_id` est POS-spécifique (préparé pour un futur funnel serveur, non peuplé actuellement) et n'a pas de sens côté SNO. **Il faudra ajouter une colonne dédiée** (ex. `channel ENUM('POS','SNO') NOT NULL DEFAULT 'POS'`) si on veut distinguer les stats — migration simple avec valeur par défaut, cohérente avec le style des migrations existantes (044 utilise déjà `ADD COLUMN IF NOT EXISTS ... DEFAULT`).

### 5. Payload SNO POST /scannorder/{slug}/upsell

Le pattern est déjà établi et cohérent sur tous les endpoints POST SNO existants : le handler décode `models.PricingRequest` depuis le body, puis écrase `req.QRCode` avec `chi.URLParam(r, "merchant_slug")` (voir `GetPricingSNO` et `CreateOrderSNO`, [handler.go:56-76](internal/modules/scannorder/handler.go#L56-L76) et [handler.go:112-129](internal/modules/scannorder/handler.go#L112-L129)). `PricingRequest.Order.Products` + `Order.OrderType` sont exactement les champs consommés par `GenerateUpsell`. **`PricingRequest` est directement réutilisable sans nouveau type**, un nouveau handler `PostUpsellSNO` suivrait le même squelette que `GetPricingSNO` en ~15 lignes.

**Côté front (`wello-resto-scannorder`, hors des répertoires de travail déclarés mais présent sur disque et lu à titre d'audit)** :
- `useUpsell` actuel ([src/hooks/useUpsell.ts](d:\Desktop\DTL\Project\git-projects\wello-resto-scannorder\src\hooks\useUpsell.ts)) est un simple `useQuery` GET, clé `["upsell", slug]`, aucune dépendance au panier.
- **Bonne nouvelle** : le pattern exact requis existe déjà dans le même repo pour `usePricing` ([src/hooks/usePricing.ts](d:\Desktop\DTL\Project\git-projects\wello-resto-scannorder\src\hooks\usePricing.ts)) — `useQuery` avec debounce 300ms sur le body, `queryKey` incluant `JSON.stringify(debouncedBody)` pour invalider automatiquement au changement de panier, `enabled` conditionné à un panier non vide. **Adapter `useUpsell` = copier ce pattern**, remplacer `calculatePricing` par un nouveau `getUpsellSuggestions(slug, body)` (POST) dans `lib/api/scannorder.ts`, à l'image de `calculatePricing`/`createOrder`. Refactor frontend **mécanique et à faible risque**, pas de nouvel adaptateur d'architecture nécessaire.

### 6. Découpage recommandé du chantier

**Phase A — Refactor cache Redis (produits individuels + reconstruction menu/upsell)**
- Apporte : élimination de la duplication par QR (clé sur `merchant_id`), invalidation granulaire par produit, suppression du goulot "6 requêtes SQL × N produits populaires" à chaque cache miss upsell.
- Dépendances : nécessite d'abord d'ajouter MGET/pipeline au wrapper Redis (prérequis technique, cf. section 3) et de décider du schéma clé (produit brut vs structure menu séparée, cf. section 2).
- Risque : **élevé sur le legacy** — touche `GetMenu`, `computeGetMenu`, `cleanProductForSNO`, la clé de cache merchant/menu/upsell existante et potentiellement `DeleteAllMerchantKeys`. Le SNO est en dev donc tolérant, mais toute régression sur `GetMenu`/`GetProduct` (fonctions legacy partagées avec le POS et d'autres intégrations — Uber Eats, Deliveroo, selon le commentaire `GetMenuFromMerchantIdWithMarketing`) peut se propager ailleurs. **À isoler strictement du module upsell POS** (ne pas toucher `menu.ListAvailableProductsForUpsell`, utilisée par le POS, dans cette phase).
- Complexité qualitative : **élevée** (nouveau schéma de cache, migration progressive, gestion de l'invalidation, tests de non-régression sur menu/fiche produit/upsell SNO simultanément).

**Phase B — Unification logique upsell (SNO appelle `GenerateUpsell` + payload panier)**
- Apporte : upsell SNO devient contextuel au panier (Apriori/LLM), cohérence produit avec le POS, et bénéficie immédiatement de la construction produit déjà "riche" (attributs/configuration) déjà en place côté SNO via `cleanProductForSNO` — à condition d'enrichir `SuggestedItem`/`GenerateUpsell` pour retourner un produit complet plutôt que les champs plats actuels (voir la partie 1 de cet audit sur `/orders/upsell`).
- Dépendances : **indépendante de la Phase A** — `GenerateUpsell` fonctionne déjà sur `menu.ListAvailableProductsForUpsell` (jointure légère), pas sur le cache produit-par-produit de la Phase A. Peut être livrée avant, après, ou en parallèle. Si on veut que les suggestions SNO retournent des produits pleinement configurés (comme aujourd'hui), il faudra soit garder un appel `GetProductFromMerchantId` par suggestion (coût déjà mesuré section 1, acceptable car borné à `upsell_max_items`, pas au catalogue entier), soit attendre la Phase A pour bénéficier du cache produit — **ordre naturel : A avant l'enrichissement produit de B, mais le branchement panier de B peut démarrer indépendamment**.
- Risque : **modéré, contenu** si on n'ajoute qu'un nouveau handler/route SNO sans toucher au code POS existant (`GenerateUpsell`, `GetUpsell` handler orders, cache Redis `upsell:result:*` restent inchangés — la fonction est déjà paramétrée par `merchantID`, aucune modification de signature nécessaire). Risque réel côté **budget LLM/coût** : le SNO génère potentiellement bien plus d'appels (tous les visiteurs anonymes vs personnel POS authentifié) — à cadrer avec des règles de fréquence/cache par panier avant activation large.
- Complexité qualitative : **moyenne** (nouveau handler + route + hook front sur pattern existant `usePricing`, pas de nouvelle abstraction).

**Phase C — Tracking upsell côté SNO (suggestion_id + acceptance)**
- Apporte : mesure de la performance upsell SNO (taux d'acceptation, revenu incrémental), symétrie analytique avec le POS.
- Dépendances : **nécessite la Phase B** (pas de `suggestion_id` sans passer par `GenerateUpsell`/`CreateSuggestion`). Nécessite aussi la migration de colonne `channel` (section 4) et de propager `UpsellSuggestionID` dans `models.RequestObject` au moment de `CreateOrderSNO` (actuellement non transmis, [service.go:827-830](internal/modules/scannorder/service.go#L827-L830)) — modification minime puisque `orderLifeCycleSvc.CreateOrder` gère déjà tout le reste du tracking (`upsellTracker.TrackAsync`) de façon générique.
- Risque : **faible** — ajout pur, ne modifie aucun comportement existant du POS ; le seul point d'attention est de bien vérifier l'ownership merchant_id dans `TrackAsync` (déjà fait, [tracker.go:88-96](internal/modules/upsell/tracker.go#L88-L96)) reste valide pour des commandes SNO créées sans utilisateur authentifié.
- Complexité qualitative : **faible**.

### Conclusion (partie 2)

**Ordre recommandé : C n'a de sens qu'après B ; B peut démarrer indépendamment de A ; A est le chantier le plus lourd et peut être mené en parallèle ou différé.** Séquence suggérée : **B (unification + payload panier) → C (tracking, quasi gratuit une fois B fait) → A (cache produit, chantier infra plus large et plus risqué, à traiter à part)**. Cela livre de la valeur produit/business (upsell contextuel + mesure) rapidement, sans dépendre du chantier cache le plus incertain.

**Points bloquants à trancher avant la Phase A** :
1. Décision de schéma : cache produit brut + cache structure séparé (recommandé, cf. section 2) vs. cache produit déjà transformé par `deliveryType` (rejeté, recrée la duplication actuelle).
2. Ajout de MGET/pipeline au wrapper Redis — prérequis bloquant, actuellement absent.
3. Décision sur la clé de cache (`merchant_id` vs `qr`) — corrige au passage le bug de duplication par QR et le pattern mort de `DeleteAllMerchantKeys`, mais implique de revoir l'invalidation pour tous les caches scannorder existants (merchant, menu, upsell), pas seulement le futur cache produit.

**Estimation qualitative** : Phase A = élevée, Phase B = moyenne, Phase C = faible.

### Suivi (2026-07-01) — doublon Kiosk résolu

Le point relevé partie 1 ("le POS devra faire un second appel pour charger la fiche
complète... à vérifier côté Flutter") avait en réalité déjà son pendant côté
**Kiosk** au moment de cet audit (pas explicitement documenté ci-dessus) :

d'appel DB redondant) et retourne `*upsell.UpsellResult` directement, même
structure que le POS, avec un nettoyage produit dédié au canal Kiosk
(`cleanProductForKiosk`) appliqué à la volée. Voir `docs/decisions.md`,
"Homogénéisation des DTO upsell Kiosk (2026-07-01)" pour le détail.
