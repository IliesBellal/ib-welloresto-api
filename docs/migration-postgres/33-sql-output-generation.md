# 33 - Generation SQL directe (structurel uniquement, aucune donnee)

Date: 2026-07-21
Branche: migration/postgres

## Objectif

Remplacer la sortie CSV du pipeline decrit dans [31-data-copy-tooling.md](31-data-copy-tooling.md)
et [32-real-export-format-check.md](32-real-export-format-check.md) par de vrais fichiers `.sql`
Postgres prets a executer, generes directement depuis `data-migration/migration_welloresto_data.sql`.
Objectif principal: eliminer l'ambiguite NULL / chaine vide du CSV en gardant le mot-cle SQL `NULL`
natif de bout en bout.

Toutes les verifications ci-dessous portent sur la structure (noms de tables/colonnes, nombres de
lignes, presence de clauses SQL) — jamais sur le contenu reel des lignes generees.

## 1. Ce qui a change dans `data-migration/transform_mysql_csv.py`

Le pipeline CSV base sur le dump (`export-table-from-dump` / `export-all-from-dump`, ajoutes dans
32) a ete remplace par un pipeline SQL equivalent:

- `generate-sql --dump <fichier> --table <table> --output <fichier.sql>` : une seule table.
- `generate-all-sql --dump <fichier> --output-dir <dossier>` : toutes les tables incluses, en un
  seul passage streaming sur le fichier (comme avant, relire 250 Mo une fois par table serait trop
  lent).

La commande `transform` (CSV standalone, workflow historique independant du dump) n'a pas ete
touchee.

### Format de sortie

Pour chaque table incluse, un fichier `NNN_table.sql` contenant:

```sql
BEGIN;

INSERT INTO table (col1, col2, ...) [OVERRIDING SYSTEM VALUE] VALUES
(...),
(...),
...
(...);

-- (autres lots de ~500 lignes si la table en a plus)

COMMIT;

SELECT setval(pg_get_serial_sequence('table', 'id_col'),
              COALESCE(MAX(id_col), 1), MAX(id_col) IS NOT NULL) FROM table;
```

- Lots de 500 lignes par instruction `INSERT` (`--batch-size` pour ajuster), toute la table dans
  une seule transaction `BEGIN;` / `COMMIT;`.
- `OVERRIDING SYSTEM VALUE` est ajoute automatiquement des qu'une colonne `GENERATED ALWAYS AS
  IDENTITY` du schema cible est presente dans les colonnes source de la table (verifie: **84**
  colonnes identity dans tout le schema cible, **toutes** declarees `GENERATED ALWAYS AS IDENTITY`,
  jamais `GENERATED BY DEFAULT` — donc Postgres refuse une valeur explicite sans cette clause des
  qu'on cherche a preserver un ID existant, pas seulement pour le cas sentinelle `tva_categories`).
- Une instruction `SELECT setval(...)` est ajoutee a la fin du fichier pour chaque colonne identity
  concernee, calculee sur `MAX(id) FROM table` apres l'insertion (pas de nom de sequence code en
  dur: `pg_get_serial_sequence` le retrouve dynamiquement).

### Transformations appliquees pendant la generation SQL

Les memes regles que le pipeline CSV, mais rendues en litteraux SQL natifs:

- Booleens (`tinyint(1)` cote MySQL) -> `TRUE` / `FALSE` litteral SQL (pas de texte).
- `merchant_id` (liste du rapport 13) -> valeur citee `'texte'`.
- `NULL` reste le mot-cle SQL `NULL`, jamais `''` ni une chaine vide.
- Nouveau (necessaire pour generer du SQL syntaxiquement correct, pas seulement du texte CSV):
  classification numerique vs texte par colonne, deduite des types declares dans
  [04-schema-postgres-target.sql](04-schema-postgres-target.sql) (`integer`, `bigint`, `numeric`,
  etc. -> litteral brut non cite ; tout le reste -> chaine SQL citee avec `'` double).
- Nouveau: une colonne `bytea` (une seule dans tout le schema cible: `kiosks.admin_pin_encrypted`)
  est convertie depuis le format hexadecimal MySQL `0x...` vers le format hexadecimal Postgres
  `'\x...'`.

## 3. Ordre de chargement et nommage des fichiers

Recherche des contraintes reelles dans le schema cible: **2 `FOREIGN KEY ... REFERENCES`** dans
tout le fichier [04-schema-postgres-target.sql](04-schema-postgres-target.sql):

- `merchant_translation_languages.lang_code -> available_languages.code`
- `product_ratings.order_rating_id -> order_ratings.id` (les deux tables de cette contrainte sont
  orphelines exclues, donc sans effet pratique sur l'ordre reel)

L'ordre de generation est calcule par tri topologique (parents avant enfants), depart alphabetique
en cas d'egalite (algorithme de Kahn). Verifie sur la generation reelle:
`available_languages` (fichier `009_...`) est bien place avant `merchant_translation_languages`
(fichier `085_...`).

Nommage: `NNN_table.sql`, `NNN` sur 3 chiffres reflete cet ordre de chargement (ex.
`001_allergens.sql`, ..., `147_without.sql`).

## 4. Deux blocages decouverts (necessitent une decision humaine)

En executant la generation sur le fichier reel, deux colonnes declarees `boolean` dans le schema
cible contiennent des valeurs source qui ne sont pas de vrais booleens MySQL (`0`/`1`). Le
generateur refuse deliberement de deviner leur sens (pas de conversion implicite "tout ce qui n'est
pas 0 devient TRUE") et **ne genere aucun fichier** pour ces deux tables tant qu'une decision n'est
pas prise. Toutes les autres tables incluses sont generees normalement dans le meme passage (voir
section 5).

### `orders.isDelivery`

- Declaree `boolean DEFAULT true` dans le schema cible ([04-schema-postgres-target.sql](04-schema-postgres-target.sql)).
- Valeurs reellement presentes dans l'export (comptage exact, aucune ligne citee):
  5 etats distincts sur 32 849 lignes (`NULL`, `0`, `1`, `2`, `3`).
- Le schema cible lui-meme documente ailleurs le sens de ces valeurs: le commentaire sur
  `tva_categories.delivery_type` precise `"0 => in, 1 => delivery, 3=> take away (2 not used
  because 2 is SNO is 'isDelivery' field or orders)"`. C'est un code a 4 etats (dine-in / livraison
  / scan-and-order / a emporter), pas un booleen.
- A l'appui: une **autre** colonne `isDelivery` existe ailleurs dans le meme schema cible, cette
  fois declaree `integer NOT NULL DEFAULT 0` (pas `boolean`).
- Conclusion probable: `orders.isDelivery` est mal type dans le schema cible (devrait etre
  `integer`/`smallint`, pas `boolean`). Ce fichier ne modifie pas le schema cible — c'est une
  decision a prendre avant de pouvoir generer et charger cette table.

### `customer.is_migrated`

- Declaree `boolean DEFAULT false` dans le schema cible, `tinyint(1) DEFAULT 0` cote MySQL source
  (aucune indication de valeurs multiples dans la DDL source).
- Valeurs reellement presentes (comptage exact, aucune ligne citee): sur 7 337 lignes —
  `NULL` (1099), `0` (5702), `1` (202), **`127`** (334). La valeur `127` n'est pas un accident
  isole: elle touche 334 lignes, donc probablement un etat delibere non documente (ex. "migre par
  un processus specifique"), pas une simple erreur de saisie.
- Aucune decision prise ici sur le sens de `127` — a arbitrer avant de pouvoir generer cette table.

## 5. Validation sur le fichier reel

Execution complete de `generate-all-sql` sur `data-migration/migration_welloresto_data.sql` (250 Mo,
591 607 lignes de donnees), sortie ecrite dans un dossier temporaire hors du repo puis supprimee
immediatement apres verification.

Resultats:

- **145 fichiers generes** (180 tables source - 1 table hors schema cible `user_status_view` - 32
  tables orphelines presentes et exclues - 2 tables bloquees `orders`/`customer` = 145).
- **974 instructions `INSERT`** au total sur les 145 fichiers ; verifie sur une table de 206 352
  lignes (`api_request_logs`) que le nombre de lots (413) correspond exactement a
  `ceil(206352 / 500)`.
- Comptage de lignes par table dans les fichiers generes: **identique**, table par table, a un
  comptage independant fait directement sur le dump brut (0 ecart sur les 145 tables).
- Verification syntaxique generique sur les 145 fichiers: parentheses equilibrees hors chaines,
  guillemets simples correctement doubles/fermes, exactement une paire `BEGIN;` / `COMMIT;` par
  fichier, `BEGIN;` avant `COMMIT;` — 0 fichier en anomalie.
- `hours_amendments` et `invoices` confirmes presents dans la sortie ; `customer` et `orders`
  confirmes absents (bloques, pas de fichier partiel/casse laisse derriere) ; aucune des 34 tables
  orphelines (nom exact, pas de correspondance partielle) trouvee dans la sortie.
- Colonne `bytea` (`kiosks.admin_pin_encrypted`, 18 lignes): 18 litteraux au format Postgres attendu
  `'\x` + 64 caracteres hexadecimaux + `'` (longueur totale 68 caracteres), confirmes
  structurellement.

### Verification specifique du point 6 : preservation du NULL

Verification demandee: confirmer que le `NULL` reste bien le mot-cle SQL natif (jamais une chaine
vide), sur un echantillon de lignes avec `NULL` sur une colonne `merchant_id`/booleenne transformee
— sans jamais citer la valeur reelle.

Colonnes booleennes/`merchant_id` avec des `NULL` reels identifies dans l'export (comptages
uniquement) :

| Table | Colonne | Type | Nombre de NULL |
|---|---|---|---|
| api_request_logs | merchant_id | merchant_id | 206 352 |
| orders | isDelivery | boolean | 17 717 |
| orders | use_customer_temporary_address | boolean | 2 671 |
| customer | is_migrated | boolean | 1 099 |
| cash_registers_custom_items | merchant_id | merchant_id | 573 |
| services_performed | confirmed | boolean | 293 |

Methode de verification (sur les fichiers `.sql` reellement generes, pas sur une re-derivation
interne) : pour chaque fichier de sortie, comptage du nombre d'occurrences du mot-cle autonome
`NULL` (hors lignes de commentaire et hors clause `setval(...) IS NOT NULL`), compare au nombre de
valeurs `NULL` attendu — calcule independamment en reparcourant le dump brut — pour **toutes les
colonnes** de la table (pas seulement booleennes/`merchant_id`).

Resultat sur les 145 fichiers generes: **943 291 `NULL` attendus, 943 291 `NULL` trouves, 0 ecart**,
table par table. Confirmation structurelle: le `NULL` est bien present comme mot-cle SQL autonome
partout ou une valeur source etait `NULL`, jamais rendu comme une chaine vide `''`. A titre de
contre-verification, des chaines vides `''` legitimes (valeurs source reellement vides, distinctes
de `NULL`) sont bien presentes separement dans plusieurs fichiers — preuve que la distinction
NULL / chaine vide, perdue dans l'ancien pipeline CSV, est desormais preservee de bout en bout.

## 6. Points de vigilance restants

- Les deux blocages de la section 4 (`orders.isDelivery`, `customer.is_migrated`) empechent la
  generation de ces deux tables tant qu'une decision n'est pas prise sur le sens des valeurs hors
  0/1 et, potentiellement, sur une correction du type de colonne dans
  [04-schema-postgres-target.sql](04-schema-postgres-target.sql).
- Les 2 lignes deja signalees dans le doc 32 (`audit_logs`, `customer`) avec un caractere de
  remplacement Unicode deja present dans le fichier source restent une anomalie de donnees en
  amont, independante de ce generateur.
- Le format `bytea` genere n'est valide que pour la forme `0x`-hexadecimal observee dans l'export
  reel ; toute autre forme leve une erreur explicite plutot que de risquer une conversion silencieuse
  incorrecte sur une colonne de donnees chiffrees.
- Rien n'a ete execute contre une base Postgres reelle a ce stade, conformement a la consigne.

## Conclusion

Le pipeline genere desormais du SQL Postgres directement executable (`INSERT` par lots de 500,
transaction par table, `OVERRIDING SYSTEM VALUE` + `setval()` automatiques pour toutes les colonnes
identity concernees) plutot que du CSV intermediaire. Verifie sur le fichier reel: 145/147 tables
incluses generees et validees structurellement sans ecart ; 2 tables bloquees par une decouverte de
donnees reelle (valeurs hors 0/1 sur des colonnes declarees booleennes) documentee ci-dessus, en
attente d'arbitrage avant de pouvoir etre generees a leur tour.
