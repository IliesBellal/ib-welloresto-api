# 04 — Notes de mapping MySQL → PostgreSQL

Source : `wello-resto-mysql-ddl.md` (dump phpMyAdmin du 2026-07-13, MariaDB 11.8.8-log, 180 tables + 1 vue).
Cible : [`04-schema-postgres-target.sql`](04-schema-postgres-target.sql) — DDL validé syntaxiquement avec le parseur PostgreSQL réel (`pglast`/libpg_query, 453 statements OK) et diffé structurellement contre la source (180/180 tables, colonnes/ordre/NOT NULL/longueurs varchar identiques, 250 defaults booléens vérifiés un à un).

## Règles de conversion appliquées

| MySQL | PostgreSQL | Remarque |
|---|---|---|
| `TINYINT(1)` | `BOOLEAN` | defaults `0/1` → `false/true` ; exceptions revues à la main (§ tinyint ambigus) |
| `TINYINT(3/4)` | `SMALLINT` | jamais converti en boolean |
| `INT(n)` / `MEDIUMINT` | `INTEGER` | la largeur d'affichage `(n)` n'a aucune sémantique |
| `BIGINT(n)` | `BIGINT` | |
| `INT/BIGINT UNSIGNED` | `INTEGER/BIGINT` + `CHECK (col >= 0)` si id/quantité | contrôle unsigned perdu (§ unsigned) |
| `AUTO_INCREMENT` | `GENERATED ALWAYS AS IDENTITY` | copie de données : `INSERT … OVERRIDING SYSTEM VALUE` puis `setval()` |
| `ENUM(…)` | `CREATE TYPE <table>_<colonne>_enum` | 13 types créés (§ enums) |
| `LONGTEXT + CHECK(json_valid())` | `JSONB` | le CHECK devient implicite |
| `TEXT/LONGTEXT/MEDIUMTEXT` | `TEXT` | |
| `VARCHAR(n)/CHAR(n)` | idem | |
| `VARBINARY(n)` | `BYTEA` | 1 colonne : `kiosks.admin_pin_encrypted` |
| `FLOAT` / `DOUBLE` | `REAL` / `DOUBLE PRECISION` | § montants en float |
| `DECIMAL(p,s)` | `NUMERIC(p,s)` | |
| `DATETIME` / `TIMESTAMP` | `TIMESTAMPTZ` | les colonnes stockent de l'UTC (audit 01/03) ; `current_timestamp()`/`utc_timestamp()` → `now()` |
| `ON UPDATE current_timestamp()` | — (supprimé) | 40 colonnes, § on-update |
| `DEFAULT '0000-00-00 00:00:00'` | — (supprimé) | invalide en PG, 2 colonnes signalées |
| collations `*_bin` | collation PG par défaut | déjà sensible à la casse, comportement inchangé |
| collations `*_ci` | collation PG par défaut | ⚠ devient sensible à la casse — § collations |
| `KEY` / `UNIQUE KEY` | `CREATE [UNIQUE] INDEX idx_/uq_<table>_<nom>` | noms préfixés (espace de noms global en PG), tronqués à 63 c. avec dédoublonnage |
| index préfixé `col(n)` | colonne retirée de l'index | 1 cas : `upsell_suggestions.accepted_items(1)` (PG n'a pas d'index préfixe) |
| FK | conservées telles quelles (2 seulement) | aucune FK nouvelle créée ; candidates listées en commentaire au-dessus de chaque table |
| Vue `user_status_view` | `CREATE VIEW` équivalente | `DEFINER`/`ALGORITHM` retirés ; `u.enabled = 0` → `= false` |

## ⚠ Impacts transverses sur le code Go (hors périmètre de ce fichier, à traiter en phase code)

1. **Booléens comparés à des entiers** : ~412 occurrences de `enabled = 1`, `available = 0`, `is_* = 1`… dans les repositories. PG ne caste pas `boolean = integer` → toutes ces clauses devront devenir `= true/false` (ou la conversion TINYINT(1)→BOOLEAN devra être revue à la baisse). C'est le plus gros impact code de la conversion.
2. **Placeholders** : `?` → `$1, $2…` (driver `pgx`/`lib/pq`) sur tout le code SQL.
3. **`LIKE` devient sensible à la casse** : 8 requêtes `LIKE ?` (bookings, kiosk, planning, scannorder, users/admin) se comportaient en insensible via les collations `*_ci` → candidates à `ILIKE`.
4. **`GENERATED ALWAYS`** : les inserts Go qui fournissent explicitement l'id auto-incrémenté échoueront (contrairement à MySQL qui l'acceptait silencieusement). Vérifier les repositories concernés ou choisir `GENERATED BY DEFAULT`.
5. **`ON UPDATE current_timestamp()`** non reproduit (40 colonnes, liste en fin du fichier SQL) : soit triggers `BEFORE UPDATE`, soit mise à jour explicite côté Go (déjà le cas dans la plupart des repositories).

## Colonnes texte candidates CITEXT / LOWER() (revue du code Go, non converties)

Comparaisons d'égalité trouvées dans les repositories sur des colonnes en collation `*_ci` (aujourd'hui insensibles à la casse, demain sensibles) :

| Colonne | Usage Go | Risque | Recommandation |
|---|---|---|---|
| `bookings.booking_number` | `WHERE booking_number = ?` (x5, recherche de résa, code potentiellement saisi par un humain) | moyen | `CITEXT` ou normaliser en majuscules à l'écriture et à la lecture |
| `barcodes.barcode` | `WHERE barcode = ?` (x4, scan) | faible (scan exact) | rien, ou CITEXT par prudence |
| `qrcodes.code` | `WHERE qr.code = ?` (x2, code embarqué dans l'URL du QR) | faible (généré système) | rien |
| `bookings_settings.code` | `WHERE bs.code = ?` (lien public de réservation) | moyen (tape/copié par des humains) | `CITEXT` ou LOWER() |
| `available_languages.code` | `WHERE al.code = ?` + FK depuis merchant_translation_languages | moyen (`fr` vs `FR`) | normaliser en minuscules |
| `brands.slug` | `WHERE slug = ?` (page publique) | moyen (URL) | normaliser en minuscules |
| `configurable_attributes.name` | `WHERE merchant_id = ? AND name = ?` (webhook Deliveroo, matching par nom) | **élevé** (matching de données externes, la casse peut varier) | `LOWER()` des deux côtés |
| `customer.customer_tel` | `WHERE customer_tel = ?` (x4) | nul (chiffres) — et la table est `utf8mb3_bin`, déjà sensible | rien |
| `customer.customer_email` | stripe webhook `WHERE customer_email = ?` ; module customers utilise déjà `LOWER()=LOWER()` | nul : table `utf8mb3_bin`, comportement inchangé | aligner le webhook sur `LOWER()` par cohérence (optionnel) |
| `users.email` / tokens | tokens comparés exacts (générés) ; pas de login par email trouvé | nul | rien |

Les recherches plein-texte (`customer_name LIKE ?`…) sont couvertes par le point « LIKE » ci-dessus.

## Defaults `'0000-00-00 00:00:00'` supprimés

`bookings.booking_date_from` et `bookings.booking_date_to` : NOT NULL conservé, le default zéro-date (invalide en PG) est supprimé — les INSERT doivent fournir la valeur (le code Go la fournit déjà). ⚠ **Les données existantes peuvent contenir des zéro-dates** : à nettoyer pendant la copie (`NULLIF`/valeur sentinelle impossible sur NOT NULL → choisir une vraie valeur ou assouplir en NULL).

## Montants/valeurs en FLOAT (risque d'arrondi, hérité de MySQL — non corrigé ici)

`barcodes.price`, `purchased_components.price`, `employment_contract.hourly_rate`, `tva_categories.tva_rate`, `components.purchase_price_quantity` → convertis en `REAL` à l'identique. Candidats à `NUMERIC` lors d'un nettoyage ultérieur (le reste du schéma stocke les montants en centimes `INTEGER`, ce qui est sain).

## Identifiants mixed-case (repliés en minuscules par PG)

`merchant.fullName/SIRET`, `merchant_calls.dateCall/TVA/HT` (+ colonnes voisines), `migration_users.createdAt/history__createdAt`, `qrcodes.QR_id`, `unit_of_measure.UOM`, `translations.creationDate`… Émis non quotés : PostgreSQL les replie en minuscules (`fullname`, `qr_id`…). Aucun impact pour le code Go qui les référence sans quotes (repli identique des deux côtés) ; en revanche, les outils de copie de données qui quotent les noms de colonnes devront utiliser la forme minuscule côté PG.

## FK candidates (non créées)

Les colonnes `*_id` dont le nom correspond à la PK d'une autre table sont listées en commentaire au-dessus de chaque `CREATE TABLE` dans le fichier SQL (143 tables concernées). Beaucoup ont des types divergents (ex. `merchant_id` tantôt `integer` tantôt `varchar` selon la table — héritage MySQL), ce qui devra être résolu **avant** de pouvoir créer de vraies FK. Décision reportée, conformément au périmètre.
