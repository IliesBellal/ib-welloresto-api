PLANNING MEMBERS + SELF-SERVICE DELTA - POSTMAN TEST PLAN

Purpose:
- This plan is the delta to run after the original planning test plan already passed.
- It covers the new backend surface added since the previous run:
  - users_rights as the establishment member profile
  - PATCH /users/{id}/member
  - login_enabled behavior in users/auth
  - employee/member bridge through employees.member_id
  - self-service planning references using me in leave, time entries, and shift swaps

Location:
- Main routes used here:
  - /users
  - /auth/login
  - /planning
- Auth:
  - all /users and /planning endpoints require the auth middleware
  - /auth/login is used to validate login behavior after member updates
- Wrapper:
  - expect the usual API wrapper with HTTP status matching the case
  - successful business payloads should still contain status=success unless the auth login flow intentionally returns another business status like user_not_allowed

PREREQUISITES

1. Assume the previous file planning-postman-tests/planning-endpoints-test-plan.txt already passed.
   Reuse its saved Postman requests and variables when possible.

2. Run the SQL scripts needed by this delta before testing.
   Minimum order for the new slice:
   - migrations/024_add_users_last_login_at.sql
   - migrations/025_add_users_rights_login_enabled.sql

3. Prepare Postman variables:

   - {{userIdMemberA}}

   - {{memberEmailA}}
   - {{userIdExistingLinkable}} optional, only if you want to test merchant-link on an already existing global user
   - {{positionIdServeuse}}

   - {{weekId}}
   - {{shiftId1}}

4. Common headers for JSON requests:

5. Suggested execution order:

   - Validate self-service planning references using me
   - Optionally validate merchant-link on an existing global user

3. AUTH / LOGIN ENABLED CHECKS
====================================================================

3.1 POST /auth/login
Purpose:
- Validate that the re-enabled member can log in.

Headers:
- Content-Type: application/json
- X-App-Source: backoffice optional; omit it if you want to avoid MFA-specific behavior during this check

Payload:
{
  "email": "{{memberEmailA}}",
  "password": "{{memberPasswordA}}"
}

Expected:
- HTTP 200 or HTTP 202 only if MFA is configured for that user
- if HTTP 200, login payload should represent a successful session

3.2 PUT /users/{{userIdMemberA}}/rights
Disable login again with the same payload as step 2.7.

Expected:
- HTTP 200

3.3 POST /auth/login
Payload:
{
  "email": "{{memberEmailA}}",
  "password": "{{memberPasswordA}}"
}

Expected:
- HTTP 200 from the endpoint itself
- business payload should indicate login refusal for the user, typically status=user_not_allowed
- this confirms login_enabled=false blocks login without hiding the member from /users

3.4 PUT /users/{{userIdMemberA}}/rights
Re-enable login one last time with the same payload as step 2.10.

Expected:
- HTTP 200

NOTES

- This file is intentionally a delta plan. Keep planning-postman-tests/planning-endpoints-test-plan.txt as the baseline core-planning pass, and use this file for the newer member/self-service slice.
- If your Postman collection already stores the original planning requests, the quickest setup is to duplicate the relevant requests and only change variables/payloads for the new member flows.
- For the me scenarios, use a token belonging to a user whose merchant membership is linked to a planning employee through employees.member_id. An admin token that is not linked to an employee will not validate the self-service path correctly.
- For auth/login checks, HTTP status alone is not enough. Read the business payload too: login_enabled=false is expected to block access via a user_not_allowed-style status while the member remains visible in /users.
